# Groq 與對話非同步排查（2026-10-06）

## 已查到的實際失敗

最近一筆對話工作失敗為 HTTP 400，錯誤要求：啟用 `response_format: json_object` 時，messages 必須包含 JSON 字樣。舊對話提示只有物件範例，沒有 JSON 字樣。此請求未成功進入模型生成，並非本機 GPU 負荷或生成逾時。

既有成功的匯入工作共有五次 Groq 呼叫，紀錄耗時約 0.59–2.17 秒；這是歷史紀錄，沒有為本次排查新增測試呼叫。

## 共用修正與範圍

| 功能 | 呼叫方式／處理 |
| --- | --- |
| 一般對話 | Tutor；一次呼叫回答與首次標題，最多六則歷史訊息，一般模式不取教材 |
| 題库文字解析 | Parser；逐題解析，保留原題，無法辨識或超過上限時提示拆分 |
| 概念分類 | Classifier；分工模式及舊 Groq 流程均以最多兩題的小批次處理 |
| AI 出題、動態考卷 | Generator；Groq 每次產生一題，限制教材、概念及近期題目上下文 |
| 最終審題 | Reviewer；分工模式最多兩題一批，API／quota／格式失敗會中止，而非當作否決後繼續花 token |
| 微課程 | Course；教學、例子、檢查、總結各一次小步驟，不要求單次生成整堂課 |
| 課程追問、錯題教學 | Tutor／LLM；保留 bounded_json 上下文預算，使用共用格式補正 |

所有文字 JSON 呼叫會補上明確 JSON 指示。共用 60 秒 API timeout、最多 800 completion tokens、16,000 UTF-8 bytes 輸入限制維持原設定。這是單次上限，不能保證不觸及 Groq 每分鐘或每日額度；HTTP 429 顯示原因及 Retry-After（若有），不自動重送生成。401／403 提示檢查金鑰與權限，截斷輸出提供明確錯誤。

目前角色設定為 Groq GPT-OSS 20B，沒有啟用本機 LLM fallback；embedding／專用 CPU 模組維持既有設定。掃描 PDF 的視覺解析仍明確提示此文字模型不支援，不自動啟動本機模型。

## 對話與非同步操作

- 使用者直接輸入第一個問題才建立對話，無需輸入標題；標題由首次回答同一次模型呼叫產生，失敗時先保留問題摘要。
- Fetch 提交，原頁輪詢狀態並顯示回答／錯誤，不跳到 AI 工作頁；重新整理可接續查看等待中的工作。
- 問題先持久化；生成失敗後不丟失，重試相同未回答問題不重複儲存。
- 對話使用獨立的兩個背景執行緒，避免排在其他帳號的大型匯入工作後；仍保留每帳號一次工作、每日額度及用量紀錄。
- 對話 API timeout 仍為 60 秒；前端等待超過 90 秒提示重新整理，不自動再次提交付費 API 呼叫。
- 記錄已閱讀以 Fetch 原地更新任務卡及月曆細節模板，不刷新頁面；不改動測驗通過判定與已完成狀態。
- CSRF、使用者資料隔離與唯讀備援保留。BODY 文件、介面、流程及資料未修改。

## 後續技術方向

目前原生 Fetch 適合處理局部表單與對話。後續可用 HTMX 讓 Flask 回傳局部 HTML，逐頁替換重新載入；SSE 適合推送狀態或逐段回答。全面改成 React／Vue 需要改寫更多資料流與模板，並非這次必要範圍。

參考：[Groq JSON 模式](https://console.groq.com/docs/structured-outputs)、[HTMX 文件](https://htmx.org/docs/)、[Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API)。

本次只進行程式、模板、腳本語法檢查與既有工作紀錄／非機密設定檢視。沒有主動呼叫 Groq、啟動本地模型或進行功能測試。成功輸出品質及實際頁面互動由使用者驗收。
